A guide to this project folder

This folder holds a B.Tech major project from Guru Nanak Dev Engineering College: a search system for Sri Guru Granth Sahib. You give it one line of Gurbani (a Pankati), and it finds other lines, from other Shabads, that carry the same meaning (Bhavarth), even when they share no words.

For example, ਵਿਸਰੀ ਤਿਸੈ ਪਰਾਈ ਤਾਤਾ (Ang 189) and ਛਾਡਿ ਵਿਡਾਣੀ ਤਾਤਿ ਮੂੜੇ (Ang 889) both teach giving up envy, yet have no word in common. Keyword search cannot connect them; this system is built to.

This page explains every folder and file: what it is, what made it, what uses it, and whether you should ever touch it. It describes the folder as of 24 October 2026.

How the pieces connect

The project is a chain of steps. Each step is one script that reads files made by the step before and writes new files. Nothing is overwritten in place, so any step can be re-run on its own.

  1. Download the scripture and its commentariesThe root scripts such as collect_gurbani.py fetched all 1,430 Angs from BaniDB and assembled the master spreadsheet final_gurbani_dataset_all_steeks.xlsx (60,360 lines, five Steeks each). This was done once.
  2. Clean itsrc/preprocessing/clean_dataset.py marks about 5,000 heading lines (such as ਪਉੜੀ ॥) so they are left out of search, and profiles the data.
  3. Split it and build the searchable corpussrc/training/create_training_pairs.py makes the list of 54,844 unique searchable verses, and splits the data into train / validation / test so that no Shabad appears in two parts.
  4. Build a test with known answerssrc/evaluation/build_eval_sets.py finds 827 test verses whose correct matches are known, by checking where two commentators explain verses alike.
  5. Build training examplesmine_verse_pairs.py finds verse pairs that mean the same thing; mine_hard_negatives.py adds a look-alike verse with a different meaning to each pair.
  6. Teach the model (needs a GPU)src/training/train_bge.py fine-tunes the BGE-M3 language model on those examples. This ran on a separate desktop with an RTX 3060 and produced the folders in models/.
  7. Turn every verse into numberssrc/retrieval/build_index.py converts each verse into 1,024 numbers that describe its meaning. Verses with similar meaning get similar numbers. Results go to data/embeddings/.
  8. Measure how good it issrc/evaluation/evaluate.py scores every model, and keyword search, on the 827-question test.
  9. Search, explain, and show itsemantic_search.py searches from the command line; explain_match.py asks a free LLM why two verses match; src/api/app.py and src/web/index.html put it all in a web page.

Rules worth knowing

Never edit the master spreadsheet.data/processed/final_gurbani_dataset_all_steeks.xlsx is the source of everything. Every script only reads it.
Never share .env.It contains a private API key. Share .env.example instead.
Use the project's own Python.Run scripts with .venv active. The older scripts in the project root are the exception: they used the computer's main Python.
Training only works on the GPU desktop.This laptop has no NVIDIA graphics card. Everything else runs here.
One heavy job at a time on the laptop.The web server and the reranker test together exceed the laptop's 11.8 GB of memory.
This is not a git repository.There is no undo history. Copy a file before making big changes to it.

Words used here

PankatiOne line of Gurbani. The unit the search works on.
ShabadA hymn: a group of consecutive Pankatis.
AngA page of Sri Guru Granth Sahib, numbered 1 to 1430.
RaagThe musical measure a Shabad is set in.
SteekA scholar's commentary explaining a Pankati. The data has five: ss Sahib Singh, bdb BaniDB (a near-copy of ss), ft Faridkot Teeka (in Braj), ms Manmohan Singh, pss a word glossary.
BhavarthThe contextual, spiritual meaning. What the search looks for.
EmbeddingA list of 1,024 numbers that represents what a verse means. Similar meanings give similar numbers, so "find similar verses" becomes "find nearby numbers".
TagA name for one model's embeddings, such as baseline or verse_hn. Each tag is a folder in data/embeddings/.
Fine-tuning / LoRATeaching an existing language model a new skill. LoRA does this by training a small add-on (9 MB) instead of the whole 2.3 GB model.
Hard negativeA verse that shares many words with another but means something different. Used in training so the model stops matching on words alone.
Gold setThe test questions with known correct answers, used to score the system.
H@10, MRRScores. H@10 is the share of test questions where a correct answer appears in the top 10 results. MRR rewards putting it near the top.

data/embeddings/

Every one of the 54,844 verses converted into 1,024 numbers, once per model. Each sub-folder is a "tag": the same verses, encoded by a different model, so models can be compared side by side. Rebuilding one takes about 2 hours on the laptop or 3 minutes on the GPU desktop.

A table of 54,844 rows × 1,024 numbers in NumPy's format. Row n is the meaning of verse n. Searching means finding the rows closest to the question's row, which takes under a second.

<tag>/corpus_meta.jsonl

<tag>/model.json
Setting
tiny

Names the model that built the tag. Typed-in text that is not already in the collection must be converted by that same model, so the search reads this file to load the right one. Present for baseline, verse_hn and mixed.

The five tags
  • baseline: the original BGE-M3 model, not trained on Gurbani. It scores below keyword search, which is why training was needed.
  • finetuned: trained on verse-and-commentary pairs. No better than baseline on the real task.
  • verse: trained on verse-and-verse pairs.
  • verse_hn: verse pairs plus hard negatives. The final model, used by default.
  • mixed: a further experiment on 40,000 mixed pairs. Weaker overall.

The experimental model behind the mixed tag: 40,000 training pairs, 3 rounds of training. Not used by default.

Inside each model folder
  • adapter_model.safetensors (9 MB): the learned weights. This is what training produced.
  • adapter_config.json: the add-on's settings (rank 16, applied to the attention layers).
  • tokenizer.json, tokenizer_config.json: how text is split into pieces the model reads. Copied from BGE-M3.
  • modules.json, sentence_bert_config.json, config_sentence_transformers.json: how the parts are assembled into one model, and the maximum text length.
  • 1_Pooling/, 2_Normalize/: the last two stages, which turn the model's output into one fixed-length list of numbers.
  • README.md: an automatically written summary of the training run (data size, loss, settings).
  • checkpoints/: snapshots from mid-training, including optimiser state. Only needed to resume training; safe to delete.

explain/explain_match.py
Code
13 KB

Explains why two verses were matched. It sends both verses and all their Steeks to a free LLM (Groq's gpt-oss-120b by default) and gets back the shared meaning in Punjabi and English, an explanation citing the Steeks, and a verdict: same, related, or different. The verdict catches the search's mistakes, for example verses that share words but teach the opposite. Answers are saved so a pair is never asked twice. Any provider with an OpenAI-style interface works (Groq, Gemini, OpenRouter) by changing .env.

Example
python src\explain\explain_match.py --query "ਵਿਸਰੀ ਤਿਸੈ ਪਰਾਈ ਤਾਤਾ" --top 3

Loads the verses and the final model's embeddings once at start-up and answers three requests: /api/search (find matching verses), /api/explain (why two verses match) and /api/health (what is loaded). It also serves the web page. It reuses explain_match.py directly so the website and the command line give identical explanations.
